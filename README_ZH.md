# HMA-Random

简体中文 | [English](README.md) | [AI 协作文档](README_AGENT.md)

HMA-Random 是一个 Zygisk 模块，用于阻止其他应用枚举你在设备上安装了什么。一句话概括：不是把应用藏起来，而是给它们换一个身份活下去。

> 本项目另有一份 [README_AGENT.md](README_AGENT.md)，承载全部设计不变量、裁决记录与红线约束。如果你正在用 AI 助手参与开发，请让它先读那份文档——这个项目的大部分约束不在代码里，在文档里。

## 核心思路

应用枚举防御长期以来是一场追赶战：查询入口散布在几十个 API 里，绕过手段（binder 直调、native 层、system uid 直接读文件）层出不穷，拦截式方案永远在补洞。

HMA-Random 不参与这场追赶。它在 system_server 注册被隐藏应用的那一刻，直接写入一个随机生成的包名 R，并为这个新身份配齐整套互相咬合的凭证：随机签名、随机标签与图标、假组件名、磁盘上可解析的诱饵 APK。从此系统里不存在「包名 P 已安装」这个事实——任何查询路径返回的都是干净结果，包括尚未被任何人想到的路径。

你可以把它理解为给应用办理证人保护：新的名字、配套的假履历、只有自己人知道真身。与拦截式方案的本质区别在于：**别人是向系统隐瞒，本模块是让系统本身成为同谋。**

代价是把谎言维护到自洽。这个项目的工程量大头不在「随机化」，而在「全套」两个字上。

## 与 HMA-OSS 的关系

名字中的 HMA 表示这是一个血统项目：与 [Hide My Applist](https://github.com/Dr-TSNG/Hide-My-Applist)（Dr-TSNG）和 [HMA-OSS](https://github.com/frknkrc44/HMA-OSS)（frknkrc44）解决同一个问题，但实现范式不同。

| 维度 | HMA-OSS | HMA-Random |
|---|---|---|
| 防御位置 | 查询层：在调用方进程内过滤结果 | 数据层：改写 system_server 的注册事实 |
| 需要维护的清单 | 拦截点（随攻击面增长） | 身份一致性通道（随系统版本增长） |
| 未知的查询路径 | 是威胁 | 不构成威胁 |
| system uid 直读文件 | 难以覆盖 | 挂载命名空间遮蔽 + 诱饵 |
| 配置形态 | 拦截规则 | 身份映射 + 策略 |

两者不共享任何代码，配置互不兼容——「能否导入 HMA 规则」的答案永远是否，因为两者的配置模型根本不同。首次发布前，我们会向 HMA-OSS 维护者说明本项目并致意。

## 设计原理

四个机制：

1. **一份身份，一次掷定。** R、随机签名、假组件名在隐藏时一次性生成并持久化，跨重启不变。不做每次查询的随机（会撕裂系统状态），也不提供随手可用的重掷（持久授权、账户、快捷方式全部按名字索引，重掷等于换了一个应用——唯一合法形态是完整的卸载再隐藏）。

2. **零拦截。** 模块只翻译两种进程：被隐藏应用自己（它必须继续相信自己是 P，否则会行为异常），以及白名单进程（启动器和设置需要显示真实的名称与图标）。对其余所有进程——包括持有 system 权限的厂商预置应用——不做任何 hook。它们不需要被拦，因为能查到的事实本来就是 R。

3. **完整的假身份。** 文件层是主战场：任何应用都能按 PMS 提供的精确路径直接打开其他应用的 APK（APK 提取器无需 root 就是证明）。因此每个隐藏应用在观察者的挂载命名空间里都有一个诱饵——一个真的 APK，用随机签名正规签过名，manifest 写着 R，体积填充到与真实应用相同的量级，目录结构与真实安装完全同构。观察者把 PMS 元数据、文件内容、签名校验三方对账，得到的仍然是一个没有破绽的世界。

4. **签名门。** 更新与探测共用安装路径，判据是密码学的：只有用真证书签名的包才被认作更新、翻译合并；伪造的试探包按「全新安装」正常落地，其全部可观察行为与「这台设备从未装过该应用」完全一致。模块会通知你有人试探，但绝不改变试探的结果——任何差别处理都会重新打开探测通道。

## 威胁模型

**有效范围**：自启用起的设备侧枚举防御。包查询、签名与元数据读取、文件枚举与直读、进程侧信道、安装试探——普通应用与 system uid 的厂商应用，得到的都是随机身份。

**边界**，逐条写明：

- 服务器侧档案不会消失。推送 token、云备份、广告标识符在你启用之前就已在远端记录了「你装过 P」。承诺从启用那一刻起算，不追溯历史。
- root 级对手与物理访问不在范围内。
- 反检测（mountinfo 挂载痕迹、注入痕迹）是继承自 Magisk 生态的长期战场：跟进、借鉴、尽力而为，但不承诺。安全叙事刻意分两层：身份反转是结构性承诺，反检测是持续军备——两者不混写。
- 被隐藏应用自身的部分功能会受损，见下节。

## 已知代价

- **商店更新断供。** 商店读到 R 与随机签名，判定「未安装」；应用内自更新仍然可用。
- **跨应用协议受损。** app-links 需要本地放行；Play 内购、以及一切「对端校验调用方包名」的握手会断——设备侧翻译骗不过别人的服务器，这是范式的固有边界。
- **维护成本。** PMS 内部结构每个 Android 大版本都重构，适配层是本模块最贵的部分。
- **软变砖风险。** 注入 system_server 的模块崩溃即软变砖。开发侧把安全模式验证列为硬性要求；用户侧请先确认你会救砖，再考虑安装。
- 完整的残余清单（dumpsys 侧信道、非 zygote 守护进程的覆盖盲区、试探包真实落地等）维护在 [README_AGENT.md](README_AGENT.md) 的 exposure_register 一节。
